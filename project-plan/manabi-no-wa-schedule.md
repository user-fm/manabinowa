## 2. 短縮の設計方針(標準計画との差分)

1. **2トラック並行化**: ボランティア軸(Flow C/D/E)と地域・安全軸(Flow F/H/I)を W04 から並行実施
2. **AI安全機能の前倒し着手**: Flow H は chat_messages のスタブデータに対して W06 から実装開始(E-10 の完成を待たない)
3. **保護者同意(K-11〜15)の前倒し**: 生徒参加機能の法令上の前提条件(§10.4、F-AUTH-07)のため **W09 までに完成必須**
4. **Classroom連携の後送**: 10週に収めるため F-GC(段階5)はリリース後へ後送(§7 縮退案1)

## 5. クリティカルパスと依存関係

- **主経路**: 段階0 → 段階1 → 段階2 → 段階3 → 保護者同意完成(W09)→ 受入(UAT)テスト(W09)→ M判定(W10)
- **スラックはほぼゼロ**。主経路上の1週遅延がそのまま 8/25 に響く
- OAuth verification(審査2〜6週)は W01 申請で最遅 W06〜W07 通過想定。M-03 のゲート条件のため未通過のままリリース不可
- 生徒参加機能は MS5(AI監視 + 保護者同意)完了が §10.4 児童保護要件上の前提
- W07〜08 の E-10(チャット)と H(AI監視)の実データ接続はトラック間の合流点。週次で進捗同期する

## 6. リスクと対策(本計画固有)

| リスク | 影響 | 対策 |
|---|---|---|
| OAuth 審査が6週を超過 | M-03 不通過でリリース不可 | W01 申請を厳守。§9.1 の最小スコープ構成で審査リスクを下げる |
| 受入(UAT)テストで重大不具合 | M-06 差し戻し・8/25 超過 | W08 から段階的に受入テストを前倒し。重大度でリリース要否を切り分け |
| 2トラック体制が確保できない | 全体 +3〜5週で 8/25 超過 | 着手前に体制を確定。不可なら目標日の再設定を判断 |
| 10週圧縮で品質不足 | リリース判定(M)で差し戻し | Classroom後送で実装量を圧縮、CASA を W06 開始で消化バッファ確保 |
| Gemini / Calendar API の想定外仕様 | 段階2/3 遅延 | W03 に両 API の疎通検証を最優先で実施 |
