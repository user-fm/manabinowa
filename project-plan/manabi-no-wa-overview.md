## 1. プロジェクト概要

### 1.1 背景

公立小中学校における教員不足が深刻化している。

- 教員採用試験の競争率は令和2年度から令和6年度にかけて約4倍から3倍程度へと年々低下
- 2024年度には受験者数・採用倍率ともに過去最低を記録
- 長時間労働と多様な校務の負担が教職の魅力を下げている
- 教員不足 → 一人あたり負担増 → 教職離れ進行、という悪循環

既存の教育系Webサービスの多くは「授業内の学習管理」に特化しており、教員の校務全体を支援するものは少ない。

### 1.2 目的

教員の校務を補助する新たなWebサービスを構築し、教員の負担を低減することで、公立小中学校教育の持続可能性を高める。

### 1.3 ビジョン

学校・地域・生徒がつながり、持続的に支え合う新しい学びのシステムを実現する。

具体的には以下の2点を達成する:

1. 学校外のサポーター(ボランティア・地域住民)の力を活用しながら、教員の負担を減らしつつ、生徒の安全性も確保する
2. 教員だけで抱えきれない部分を地域の大人が支えることで、学校全体の余裕を生み出し、より質の高い学びを提供できる環境を整える

## 2. ステークホルダー

| 役割 | 概要 | アカウント種別 |
|---|---|---|
| 教師 (Teacher) | 公立小中学校の教員。ボランティア依頼、地域依頼の確認・選定を行う | 学校のGoogle Workspaceアカウント |
| 生徒 (Student) | 公立小中学校の児童・生徒。ボランティア指導を受ける | 学校のGoogle Workspaceアカウント |
| ボランティア (Volunteer) | 学習支援・部活動支援を行う希望者 | 個人Gmailアカウント |
| 地域住民・団体 (Community) | 学校への依頼を出す地域住民・地域団体 | 個人Gmailアカウント |
| 学校管理者 | 校長・教頭・ICT担当等。AI監視アラート受信、ブロックリスト申請、本運用判定を行う | 学校のGoogle Workspaceアカウント |
| 教育委員会 | 自治体教育委員会担当者。月次監査レポート閲覧、統計ダッシュボード閲覧を行う | 学校のGoogle Workspaceアカウント |
| 保護者 (Parent) | 児童生徒の保護者。生徒ロール登録時に電子署名による同意手続きを行う | アカウント不要(メールリンク経由で電子署名) |
| サービス運営者 | 「まなびのわ」運営主体。個人Gmailアカウント審査、ブロック申請審査、削除要求の本人確認、問い合わせ対応を行う | 管理者用アカウント |

> **システム上の名称(actor_type)**: 6ロールは `users.role` の英識別子(teacher/student/volunteer/community/admin/board)で扱う。`users` に載らない主体も `actor_type` で一元化する ── サービス運営者=`operator`(`operators` 表)、保護者=`parent`(`consent_records.token`)、システム=`system`、AI=`ai`(定数識別子)。詳細は `manabi-no-wa-database.md` §1.4。

## 3. サービスの2軸

### 3.1 軸1: 学校ボランティアのオンライン化

**現状の課題:**
- 公立学校の学校ボランティアは自治体の教育委員会で募集されるため、希望者は基本的に自分の住む自治体にしか応募できない
- ボランティアの方の都合と学校側の都合を合わせるのが困難

**まなびのわで実現すること:**
- ボランティアが全国の教育委員会の依頼に応募可能
- オンライン上で学習支援・部活動支援を実施
- アフタースクール支援、授業補助などに柔軟に対応可能
- ボランティア人材の分散配置により、教員の負担を低減

### 3.2 軸2: 地域連携

**現状の課題:**
- 地域住民・団体からの依頼(ポスター制作、行事参加など)が教員個人に集中
- 細かな連絡・調整の負担が大きい

**まなびのわで実現すること:**
- 地域からの要望・依頼を一括して受付
- 教員は自校に関連する依頼のみ確認・選定
- 受け入れた依頼を探究学習や課外活動の教材として活用
- 地域の歴史・伝統文化を伝える機会を創出

#### 採用しなかった / 変更した候補

| 元の候補 | 変更 | 理由 |
|---|---|---|
| BetterAuth | → Supabase Auth | RLSと密結合、6ロール権限をDBで宣言的に |
| AWS SES | → Resend | 初期セットアップ軽量、後でSES移行容易 |
| AWS SQS | → Supabase Queues (pgmq) | DB同一トランザクション、Edge統合容易 |
| OpenSearch | → pgvector + pg_trgm | コスト効率、運用負荷低。pgroongaはSupabase非対応 |
| Prisma | → Drizzle | RLS互換性、Edge対応、Supabase統合事例 |
| Terraform/CDK | → 当面なし | 現構成ではIaC対象なし |
| SkyWay | → Google Meet | コスト効率、学習コストゼロ |
| GiNZA + FastAPI | → Vertex AI (Gemini) | 統合・精度・コスト効率、別サーバ不要 |


## 10. セキュリティ・プライバシー

### 10.1 適用法令・ガイドライン

- 個人情報保護法(2022年改正)
- 学校DXガイドライン(文部科学省)
- 教育情報セキュリティポリシーガイドライン(総務省)
- 児童ポルノ・児童虐待防止法

### 10.2 セキュリティ対策

- HTTPS 必須(HSTS 有効化)
- CSP (Content Security Policy) 設定
- Supabase Row Level Security
- Sentry によるエラー監視
- 定期的な依存関係セキュリティスキャン(GitHub Dependabot)
- CVE-2025-55182 パッチ適用済みバージョン使用

### 10.3 データ保護

- 全データは日本国内(Tokyo region)に保管。AI推論も Vertex AI(asia-northeast1)に固定し、入力は学習に使用しない。チャット原文の永続保管は Supabase(Tokyo)のみ
- 機微情報(チャット履歴等)はAPI経由のみアクセス
- 監査ログは最低3年保管
- 削除要求対応(個人情報削除フロー)

### 10.4 児童保護

- ボランティアの本人確認(メール認証 + プロフィール審査)
- **児童保護の必須担保は「セッションのチャット全文ログ + AI監視」とする**(録画可否は学校のWorkspaceエディションに依存するため、これに依存しない)
- 録画は可能な学校で実施し、リンクは教師が手動登録(学校管理者は閲覧可能)。自動取得は将来 Meet API で対応(F-SES-07)
- AI による不適切発言の自動検知(監視対象はセッション内チャット F-NTF-03 に限定。大人のみのロール間メッセージ F-MSG は児童が関与しないため対象外)
- 学校側からのブロックリスト機能
- 保護者同意フローの実装

## 12. 収益構造

### 12.1 コスト

| 項目 | 種別 | 概算 |
|---|---|---|
| Vercel ホスティング | 固定費 | $20/月〜(Pro Plan) |
| Supabase | 固定+従量 | $25/月〜(Pro Plan)、利用量に応じてスケール |
| Gemini API | 従量 | 月数千〜数万円(利用規模次第) |
| Resend | 従量 | 月3000通まで無料、以降従量 |
| Sentry | 固定+従量 | $26/月〜 |
| ドメイン・SSL | 固定費 | 年額数千円 |

### 12.2 収益源

- 自治体が実施する放課後事業の委託料
- 部活動指導員の配置に関する予算
- 学校・教育委員会との直接契約
- ボランティアと教育委員会の契約はボランティアの方自身が行うことで長期的運用を確保

### 12.3 アピールポイント

1. **国内データ保管**: ログイン認証や個人情報を、自治体での運用実績が豊富な国内サーバーに保存
2. **持続可能な収益構造**: ボランティアと教育委員会の契約は本人同士のままで、まなびのわはインフラ提供に徹する
3. **段階的導入可能**: 小規模から必要に応じて段階的に拡大でき、学校側のリスクを最小限に抑制

## 13. リスクと対策

### 13.1 技術リスク

| リスク | 対策 |
|---|---|
| Next.js / React の脆弱性 | Dependabotで自動監視、セキュリティパッチ即適用 |
| Supabase 障害 | 重要データの定期バックアップ、SLA確認 |
| Vertex AI(Gemini)料金高騰 | 月次コスト監視、検知頻度・対象メッセージの最適化 |
| OAuth verification 不通過 | 申請を早期着手、必要書類事前準備、スコープ最小化 |
| RLSの素通り(Drizzle固定ロール接続) | ユーザー文脈はsupabase-js経由、Drizzleは信頼ジョブのみ(§6.2 データアクセス方針)。RLSポリシーのテストをE2Eに含める |
| Realtime同時接続が上限超過 | 1セッション=1チャンネル設計、add-onでサイジング、W09/W11で実測・負荷試験 |
| Meet録画が `drive.file` で取得不可 | 初期は手動登録、児童保護はチャット全文ログ+AI監視で担保、自動化はMeet API |

### 13.2 運用リスク

| リスク | 対策 |
|---|---|
| ボランティアの不適切行為 | 本人確認、AI監視、ブロックリスト、チャット全文ログ(可能な学校は録画) |
| 生徒の個人情報漏洩 | RLS厳格化、機微情報暗号化、監査ログ |
| 学校WorkspaceがMeetの外部参加を制限 | 導入前(W05)に外部参加可否を確認。不可なら運営側Workspaceがオーガナイザーになる代替を用意 |
| 自治体ごとの規則対応 | 自治体ヒアリング、柔軟な設定機能 |
| 利用校が広がらない | 段階的導入で実績蓄積、文部科学省・自治体への働きかけ |

### 13.3 法令リスク

| リスク | 対策 |
|---|---|
| 個人情報保護法違反 | プライバシーポリシー整備、定期監査 |
| 児童保護法令違反 | AI監視、保護者同意、録画 |
| 自治体個別条例 | 自治体担当者との事前協議 |
